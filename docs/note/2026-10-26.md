# 2026-10-26 · 客户端表现层：为什么是 MVP，以及 Flux 能借什么

> 非正式学习笔记。不是决策记录；正式结论见 `docs/architecture.md` / `docs/roadmap.md` / `docs/design/`。
> 目标：把"客户端表现层怎么组织"的推理过程讲清楚，而不只是给结论。

## 0. 先问：客户端到底在做什么

客户端只有两条数据流：

```
服务器事件 ──▶ 更新展示状态 ──▶ 画给用户看
用户输入   ──▶ 变成命令     ──▶ 发给服务器
```

关键事实：**客户端不拥有权威状态**。

- 发牌、行动是否合法、谁赢、分多少，都以服务器为准；
- 客户端的状态只是**服务器事件的投影**；
- 用户的操作是**命令（intent）**，不是直接改状态。

这条事实决定了后面所有架构选择。

## 1. 从 MVC 到 MVP

### 1.1 经典 MVC 的三件套

```
用户输入 ──▶ Controller ──▶ Model（改状态）
                              │ 通知
                              ▼
                            View（重绘）
```

- **Model**：领域状态 + 规则；
- **View**：观察 Model，负责显示；
- **Controller**：把输入翻译成对 Model 的操作。

### 1.2 直接套到客户端，为什么会别扭

三个原因：

1. **"Model" 的歧义**
   经典 MVC 的 Model 是**领域模型**；但客户端的 `ClientModel` 只是**展示状态（投影）**。领域模型在服务器。把投影叫 Model，容易和服务器模型混淆。

2. **View 订阅 Model 的耦合**
   经典 MVC 里 View 观察 Model 的变化。放到 C++ 控制台里，这意味着 Model 要持有 View 的引用/回调，或者引入观察者机制。对一个小客户端来说，**多了一层不必要的耦合**。

3. **Controller 的职责不清**
   你的 `ClientController` 既要处理**服务器事件**，又要处理**用户输入**，还要更新模型、触发重绘。如果再用经典 MVC 的"Controller 只管输入"，就不匹配了。

### 1.3 更贴合的形状：MVP（被动视图）

```
             ┌──────────── Presenter ────────────┐
服务器事件 ──▶│ 更新 Model；调用 View；发命令      │──▶ ServerGateway（命令）
用户输入   ──▶│                                    │
             └───────────┬───────────┬────────────┘
                         ▼           ▼
                    ClientModel   ClientView（被动，只 render）
```

- **Model / ViewModel**：`ClientModel`，纯展示状态；
- **View**：`ClientView`，只有一个 `render(const ClientModel&)`，**被动**；
- **Presenter**：`ClientController`，负责：
  - 接收服务器事件（`ClientHandler::on`）；
  - 把事件投影到 `ClientModel`；
  - 调 `ClientView::render`；
  - 在轮到自己时，向 `PlayerInput` 要一个命令，再经 `ServerGateway` 发出去。

### 1.4 为什么被动视图更好

- **可测试**：View 不订阅、不回调、不碰网络；用 fake view 记录 `render` 调用即可。
- **可替换**：控制台 → GUI，只换 `ClientView` 实现，Presenter/Model 不动。
- **单向**：事件 → 模型 → 视图，没有双向绑定，调试路径清楚。
- **职责清晰**：View 不写规则，Presenter 不写格式化细节。

## 2. 映射到本项目

| 角色 | 现有/建议 | 说明 |
|---|---|---|
| Presentation Model | `ClientModel` | 服务器状态的投影；补 `stage/acting_seat/round_bet/min_raise/revealed` 等 |
| View | `ClientView` / `ConsoleView` | 只 `render(model)`；不订阅、不发命令 |
| Presenter | `ClientController` | 实现 `ClientHandler`；持有 `ServerGateway&`、`ClientView&`、`PlayerInput&` |
| 入站端口 | `ClientHandler::on(GameEvent)` | 服务器事件入口 |
| 出站端口 | `ServerGateway::send(GameCommand)` | 用户命令出口 |
| 输入策略 | `PlayerInput`（建议新增） | 人类/脚本/Bot 可替换 |
| 格式化 | `Formatter`（纯函数） | 牌、筹码、阶段、动作、状态 |

依赖方向：

```
ClientView ──依赖──▶ ClientModel（只读）
ClientController ──依赖──▶ ClientModel / ClientView / ServerGateway / PlayerInput
ClientModel ──不依赖──▶ 任何 I/O
```

## 3. 两条数据流（详细）

### 3.1 入站：服务器事件 → 视图

```
ClientHandler::on(GameEvent)
    └─ std::visit → handle(具体事件)
        ├─ 更新 ClientModel
        └─ view.render(model)
```

- 事件是**事实**：发了什么牌、谁做了什么、谁赢了。
- 投影只做"把事实写进展示状态"，不做规则判定。
- 私密信息（底牌）只会在 `HoleCardsDealt` 里给自己，或在 `HoleCardsRevealed` 里公开。

### 3.2 出站：用户输入 → 命令

```
TurnStarted（轮到自己）
    └─ Presenter 更新模型并渲染
        └─ PlayerInput::decide(model) → optional<GameCommand>
            └─ ServerGateway::send(command)
```

**纪律**：不要在本地"先改状态再发服务器"。客户端没有权威；本地乐观更新会导致和服务端不一致（扑克尤其危险）。

## 4. 为什么需要 `PlayerInput`

现在 `ClientController::handle(TurnStarted)` 里是硬编码的 check/call。这在 demo 里够用，但：

- 人类玩家需要选动作；
- 测试需要可脚本化；
- Bot 需要可替换策略；
- 以后 GUI 需要不同输入方式。

所以抽一个策略接口：

```cpp
class PlayerInput {
public:
    virtual ~PlayerInput() = default;
    // 返回 nullopt 表示"这次不行动/超时/交给上层处理"
    virtual std::optional<GameCommand> decide(const ClientModel& model) = 0;
};
```

Presenter 里的用法：

```cpp
void ClientController::handle(const Event::TurnStarted& event) {
    update_model(event);          // reducer：stage/acting/round_bet/min_raise…
    view.render(model);

    if (event.player != model.this_player_seat) return;

    if (auto command = input.decide(model)) {
        server_gateway.send(*command);
    }
}
```

实现：

- `ConsoleInput`：打印可选动作，读 `fold/check/call/raise <amount>`；
- `ScriptedInput`：测试用，按预设序列返回命令；
- `BotInput`：随机/紧凶等策略；
- 未来 GUI：`GuiInput`。

**合法性**：展示层可以用共享的纯查询（`legalActions` 等）来禁用非法按钮/选项，但**最终以服务器校验为准**。

## 5. Flux / Redux 是什么

### 5.1 核心：单向数据流

```
View ──Action──▶ Dispatcher ──▶ Store ──▶ View
```

- **Action**：描述"发生了什么"的数据；
- **Dispatcher**：中央分发；
- **Store**：持有状态、处理 action、通知 View；
- **View**：渲染 + 派发 action。

**Redux** 是 Flux 的变体：单一 Store + 纯 reducer（`next(state, action)`）+ 不可变状态 + 中间件。

### 5.2 最适合什么

- 状态复杂、组件多、共享状态多的**客户端 UI**；
- 需要可预测更新、时间旅行调试、撤销/重做；
- 多屏/多组件依赖同一份状态。

### 5.3 不适合什么

- 简单 UI、单屏、状态很少；
- **服务端权威**的多人游戏——因为 Flux 默认 action 在本地改 store，而你的权威状态来自服务器。

## 6. 映射到本项目：能借什么，不能借什么

### 6.1 你已经有的"Flux 精神"

| Flux | 本项目 |
|---|---|
| Store | `ClientModel`（单一状态源） |
| Reducer | `handle(event)` / 未来的 `next(state, event)` |
| View | `ClientView` |
| Action | 服务器事件；用户命令是另一条方向 |
| Dispatcher | `std::visit` / `ClientController` 的分发 |
| 单向流 | ✅ 事件 → 模型 → 视图；输入 → 命令 → 服务器 |

### 6.2 能借的

- **单一状态源**：所有展示状态放 `ClientModel`，不散落。
- **纯 reducer**：把"事件 → 状态"写成无副作用的函数，方便测试/回放。
- **单向数据流**：不要 View 直接改 Model，不要 Model 反向调 View。

### 6.3 不要借的

- **Dispatcher**：`ClientController` + `std::visit` 已经够了。
- **多 Store / 订阅系统**：单屏客户端不需要。
- **不可变状态库 / 中间件 / 时间旅行**：除非以后 GUI 变复杂。
- **乐观更新权威状态**：服务端权威，必须等服务器事件。

### 6.4 关键差异：谁拥有"真相"

这是最值得记住的一点：

- **Flux/Redux 假设客户端 Store 是真相**，action 在本地改状态；
- **本项目服务器才是真相**，客户端 Store 只是**投影**；用户动作是"请求"，不是"事实"。

所以正确的心智模型是：

```
用户动作 ──命令──▶ 服务器 ──事件（事实）──▶ 客户端投影 ──▶ 视图
```

而不是：

```
用户动作 ──本地改 store──▶ 视图
```

这也是为什么"完整 Flux/Redux 框架"对多人游戏是错配的，但它的**单向流 + 单 store + reducer** 思想完全适用。

### 6.5 什么时候值得上更接近 Redux 的结构

如果以后客户端变成复杂 GUI（大厅、设置、聊天、多桌、动画、撤销/重做），可以手写一个 Redux-like store：

- `ClientModel` 当 Store；
- `next(state, event)` 当 reducer；
- `ClientView` 订阅/重绘；
- 本地 UI action 与"发给服务器的命令"分开。

但**现在不需要**。

## 7. 与"函数式核心 + 命令式外壳"的关系

客户端也可以这样分：

- **函数式核心**：`next(ClientModel, GameEvent) -> ClientModel`（纯 reducer）；
- **命令式外壳**：`ClientController`（I/O、渲染、发命令）。

好处：

- reducer 可以单测、回放、对比；
- 外壳很薄，容易替换（控制台/GUI/网络）；
- 和服务器侧的"事件 → 状态"思路一致（对称）。

## 8. 推荐落地步骤（增量）

1. **补 `ClientModel`**：`stage`、`acting_seat`、`round_bet`、`min_raise`、`can_raise`、`revealed_cards`、赢家/分池摘要、连接状态。
2. **抽 reducer**：把 `ClientController` 里的投影逻辑集中到 `apply(ClientModel&, const GameEvent&)` 或 `next(...)`。
3. **加 `PlayerInput`**：`ClientController` 在 `TurnStarted` 时调用它，不再硬编码 check/call。
4. **被动 View**：`ClientView::render(const ClientModel&)` 不变；`ConsoleView` 注入 `std::ostream&`，不要直接 `std::cout`。
5. **测试**：
   - reducer 单测（构造事件序列 → 断言模型）；
   - Formatter 纯函数金样例；
   - Presenter 用 fake view / fake gateway / scripted input 测；
   - ConsoleView 用 `ostringstream` 快照。
6. **接线**：改写 `src/client_main.cpp`，用 `ClientController` + `ServerGateway`（网络适配器）+ `ConsoleView` + `ConsoleInput`。

## 9. 常见错误

1. **View 直接发命令**：View 只读模型；命令必须经 Presenter。
2. **Presenter 里算赢家/底池**：以服务器事件为准；展示层最多用共享纯函数。
3. **客户端乐观更新权威状态**：会和服务端分叉。
4. **View 订阅 `EventBus`/网络**：View 只依赖 `ClientModel`。
5. **Model 里塞展示字符串**：文案放 Formatter/View，模型保留领域值。
6. **全局单例 Store**：隐藏依赖，难测试；用注入。
7. **把 MVC 的 "Model" 当成服务器领域模型**：客户端 Model 是投影，不是规则引擎。

## 10. 一句话

> **客户端用 MVP：`ClientModel` 是 ViewModel，`ClientView` 是被动 View，`ClientController` 是 Presenter；输入通过 `PlayerInput` 策略，命令经 `ServerGateway`。Flux/Redux 的单向流、单 store、纯 reducer 值得借；Dispatcher/多 Store/本地权威更新不要借——因为真相在服务器。**
